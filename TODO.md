**Three durable findings about deploying here, worth more than any PID:**
- **A migration must land BEFORE the plugins that depend on it**, and this applies to the Vercel deploy too. Reversed, footers carry a field whose column doesn't exist, Prisma throws inside ingest's blanket `try/catch`, and listings silently stop being tracked while every reply still looks perfect.
- **A gateway restart reuses the WhatsApp bridge ONLY IF that bridge is healthy AND current — otherwise it kills and replaces it.** This was recorded as the unconditional "a restart reuses the existing bridge, so the live session survives untouched", and that is **wrong**; it cost a real outage on 2026-07-29. Read from `plugins/platforms/whatsapp/adapter.py`: reuse requires `/health` to report `status == "connected"` **and** the running bridge's `scriptHash` to equal the on-disk `bridge.js` hash. Fail either and it runs `_kill_stale_bridge_by_pidfile` + `_kill_port_process` and spawns a new one. Every previous observation ("up since 07-24 across every restart") was a healthy bridge, so the condition never showed. **The operational consequence is the dangerous part: restarting a gateway whose bridge is already struggling destroys the connection that might have recovered on its own** — and note `hermes update` also changes `bridge.js`, so the hash check replaces the bridge after any update. **Pairing itself is never lost either way** — the session lives on disk and the phone keeps the linked device; it is the *connection* that is thrown away, and reconnecting is not guaranteed to be quick.

## 📸 13. Listing photos and videos, end to end (SCOPED 2026-07-29, not started)

**The ask:** the agent sends photos/videos of a property to the operator bot along with the facts; they are recorded against the `Listing`, shown in the reporting app, and the **buyer bot sends them to a buyer who asks**. No code written; this is the feasibility scoping, done by reading and running the vendored Hermes source.

**Verdict: possible, and two of the three legs already exist.** The security half of the scoping was acted on immediately — see the closed deploy gate above.

**What Hermes already gives us, verified in the source:**
- **Inbound is free.** The Baileys adapter downloads and caches inbound media per-profile (`image_cache/`, `video_cache/`, `cache/videos/`) and recognises `.mp4/.mov/.avi/.mkv/.webm/.3gp` (`plugins/platforms/whatsapp/adapter.py`). Photos already reach the model via the vision pre-analysis path documented in PR #14. **Video is cached but never analysed** — the model knows a video arrived, not what is in it.
- **Outbound needs no new tool, which was the surprise.** Delivery is triggered by the model emitting a path in reply text; the gateway strips it and dispatches `send_multiple_images`/`send_video`/`send_document`. WhatsApp video plays inline. **So the buyer instance's 3-tool lockdown does not have to be touched** — good for feasibility, and precisely why the deploy gate above was open. **Two triggers, not one (corrected 2026-07-31):** an explicit `MEDIA:<abs path>` tag (`extract_media`) *and* a bare absolute / `~/` / drive-letter path merely mentioned in the reply (`extract_local_files`, which exists precisely to ship artifacts "without needing an explicit `MEDIA:` tag"). Both are filtered through the same `validate_media_delivery_path`, so the buyer lockdown covers both — but design item 13's delivery against both, not just the tag.

**The three real problems, in descending order of how much work they are:**
- [ ] **Getting files from the operator box to the buyer box — this is the actual build.** In production they are *different machines*, and `MEDIA:` needs a local absolute path on the *buyer* instance. So: capture → blob storage → reference on `Listing` → materialise onto the buyer box (or into its cache roots, which are the allowlisted delivery dirs). Postgres/Neon is the wrong home for video. **Store decided — Cloudflare R2, see the block below.**
- [ ] **Plugin hooks cannot see attachment paths.** The kwargs are the six established when the null-`buyerContact` bug was fixed (`conversation_history`, `is_first_turn`, `model`, `sender_id`, `task_id`, `telemetry_schema_version`) — no media. So `sync-to-webapp` cannot record media the way it records text; capture needs another route (read the profile's cache dir, or the adapter's stored message row).
- [ ] **Making the model emit `MEDIA:` for the *right* listing is the known compliance-gap class.** Getting a model to reliably *do* a thing via in-context text has failed three times here ([[project_gateway_footer_omission_bug]], PR #26, PR #28). The reliable channel is always-injected plugin text, as `listing-footer-reminder` already does. Plan for that up front rather than discovering it live.

**DECIDED 2026-07-29 — blob store: Cloudflare R2.** Owner-approved. Nothing account-level actioned: **no Cloudflare account created, no bucket, no credentials.** Reasoning in CLAUDE.md; the short form is that this architecture is unusually egress-heavy (every file crosses machines at least twice before anyone sees it) and R2 charges zero egress, and that R2's S3 compatibility means one API serves both runtimes — `@aws-sdk/client-s3` in Next.js and `boto3` on the Hermes box. Rejected, with reasoning: **Vercel Blob** (right if media were only ever shown in the dashboard, but the buyer box is a first-class consumer sitting outside Vercel, and there is no Python SDK), **S3** (re-imports the per-GB egress and IAM overhead AWS was already rejected for on compute), **Backblaze B2** (genuinely competitive, no objection if preferred later; R2 won on zero-egress being unconditional rather than a storage-ratio allowance).
- [ ] **Create the Cloudflare account + bucket** (account-level, owner). This is step one and unblocks the rest of item 13. Check at signup whether a payment method is required to enable R2 even inside the free tier — not asserted here either way.
- [ ] **Re-check R2 pricing before committing.** Cost at pilot scale is expected to be **zero** — the free tier (~10 GB) covers roughly 3 customers × 50 listings × 15 photos + a video several times over. That is a projection from a knowledge cutoff, and this repo has already been bitten by stale third-party pricing (see 12b on Meta). Verify, don't inherit.
- [ ] **Private bucket, per-customer key prefix, presigned URLs — never public objects.** A public URL is a permanent unauthenticated link to a customer's property media, and once it is pasted into a WhatsApp thread there is no way to revoke it.
- [ ] **The buyer box gets a read-only, prefix-scoped credential, not the operator's.** Same split, and the same reasoning, as the operator/buyer ingestion secret closed on 2026-07-27: it is the one public box, and the tool lockdown says nothing about what a credential can reach. Cheap at design time; retrofitting it cost a whole PR last time.

**Constraints to carry into any implementation:**
- **Write media into the profile cache roots** (`cache/{images,audio,videos,documents}`, `image_cache/`, `video_cache/`). They are allowlisted *before* the denylist is consulted, so they survive the strict-mode lockdown above. Anywhere else is now undeliverable on the buyer instance, by design.
- **Do not re-enable `vision` on the buyer profile.** It is off because a public instance processing attacker-supplied images is what makes the deferred Pillow CVEs (item 6) reachable. Sending media *out* does not need vision, so there is no reason to.
- Same buyer-side honesty rule as `Features:` — media that is absent must read as *unknown*, never as "there are no photos".
