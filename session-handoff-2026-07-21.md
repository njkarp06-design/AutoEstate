### Decisions Made

- **Project name: AutoEstate.**
- **Target industry: independent real estate agents in Tel Aviv** (not franchises). Why: sharp recurring pain (constant listing content, no time to write it), WhatsApp/Facebook-group-native distribution fits the local market, ~450-570 agents in Tel Aviv is a big-enough market, and the user has warm local network access for a pilot.
- **Self-hosted Hermes, not Nous Portal.** Why: full control, no third-party auth dependency in the loop for what's meant to be a security-differentiated product.
- **Phase 2 first workflow: listing-to-social pipeline**, specifically split into two sub-phases:
  - **2a (done this session):** the skill itself — facts in, formatted bilingual captions out. No WhatsApp, no auto-posting. Deliberately built and tested this way first so we could validate content quality before taking on messaging-integration risk.
  - **2b (in progress):** wire up WhatsApp as the actual trigger.
- **WhatsApp integration: Baileys/QR bridge, not the official Business Cloud API — for now.** Baileys emulates a linked WhatsApp Web device (no Meta Business verification, no public server needed, works from a laptop). Tradeoff knowingly accepted: this violates WhatsApp's ToS for automated use and carries a real, unpredictable ban risk (researched: WhatsApp's own detection can flag an account anywhere from immediately to months in — no reliable pattern). Business Cloud API is the correct production path later (Phase 5 territory) once this is validated enough to matter — it requires a Meta Business account and a publicly-reachable server, neither of which we have yet.
- **Use a dedicated number for the WhatsApp bot, not the user's personal number** — specifically to contain the ban risk above. Decided approach: an **eSIM** with a new number, registered on the **WhatsApp Business app** (a separate app from regular WhatsApp, so it runs alongside the user's personal WhatsApp on the same phone with no conflict — confirmed this works fine technically since Baileys treats Business and regular WhatsApp identically).
- **Keep at least a minimal active plan on that eSIM rather than fully disabling it.** Why: the phone only needs *internet* (wifi is fine) every 14 days to keep WhatsApp's linked-device session alive, but if WhatsApp ever demands SMS/call re-verification (plausible specifically *because* this is automated bot activity), a fully dead SIM would cause an unrecoverable lockout. Cheap insurance against an uncertain but real failure mode.
- **Ruled out WhatsApp's "self-chat mode" as a way to test before the eSIM arrives.** Considered it as a lower-risk substitute for pairing to a personal number, but the official docs describe bot mode (dedicated number) as "lower ban risk" and self-chat as just "quick setup, single user, testing" — no stated risk reduction, and it still runs on the personal number via the same unofficial Baileys bridge. Not a real shortcut, correctly abandoned.
- **Validated the gateway pipeline without WhatsApp, using a disposable Telegram bot instead.** Telegram's official bot API carries zero ban risk and needed no phone number. Confirmed end-to-end: real inbound message → allowlist → skill fires → reply delivered, all through the same gateway process WhatsApp will use. This means once the eSIM lands, pairing is the only unverified step left — everything downstream is already proven.
- **Ran a further round of gateway edge-case testing against the same Telegram bot** (still 2026-07-21, later in the day), to make more progress while blocked on the eSIM. Four scenarios tested, all against a live `hermes gateway` process with `gateway.log` tailed directly:
  1. **Unauthorized sender** — temporarily pointed `TELEGRAM_ALLOWED_USERS` at a dummy ID, sent a real message from the actual account. Log confirmed: `Blocked unauthorized user 8543293827 in chat 8543293827` — rejected at the Telegram adapter before reaching the agent or skill at all. No reply sent. Allowlist restored afterward.
  2. **Gateway restart/recovery** — killed the running gateway process mid-session, restarted it. Reconnected to Telegram cleanly in ~2 seconds, no leftover lock/state issues.
  3. **Non-listing message** — sent "Hi" as an authorized user. Got a natural short reply ("Hey Natanel! Whats up?"), not a hallucinated attempt to treat it as listing facts.
  4. **Rapid consecutive messages** — sent 3 short listing-fact fragments back-to-back (mimicking how a real agent might type on WhatsApp). Result: the skill did **not** cleanly batch all 3 into one pass — it asked follow-up questions across a couple of extra rounds before producing the correct final listing. Root-caused via the vendored adapter source (`plugins/platforms/telegram/adapter.py`), not guessed: each turn takes 10-20s of real LLM latency, and `busy_input_mode: interrupt` (config.yaml default) treats any message arriving mid-turn as an interruption to merge in, rather than something to wait for. This is **not** a fixable batching-window problem — the adapter hardcodes a 0.18s "fast path" delay for any accumulated text ≤320 characters via `min(operator_setting, 0.18)`, so raising `HERMES_TELEGRAM_TEXT_BATCH_DELAY_SECONDS` (which is also hard-clamped to a 2.0s max in code regardless) has **no effect** on realistic short fact-fragments — verified by reading the source before touching config, not by trial and error.
  - **Also investigated and explicitly ruled out:** typing-indicator-based delay ("wait while the user is composing"). Telegram's Bot API doesn't expose the other party's typing status to a bot at all (bots can only push a typing indicator outward, not receive one). Baileys (WhatsApp) *can* technically receive presence/composing updates via explicit per-chat subscription, but Hermes's built-in WhatsApp bridge (`scripts/whatsapp-bridge/bridge.js`) currently only sends typing indicators, never listens for incoming presence — adding that would mean owning custom modifications to vendored bridge code, would still need a timeout fallback for reliability (WhatsApp privacy settings can suppress presence delivery), and can't even be validated against the Telegram stand-in first. Decided not worth building.
  - **Decision: leave `busy_input_mode: interrupt` and the batch-delay defaults as-is.** The multi-round behavior self-corrects (ended with the right listing) and the actual cost driver is LLM turn latency, not a config knob — patching vendored adapter code to chase this was judged not worth it before it's shown to matter in real agent use. Revisit only if this proves genuinely annoying once real WhatsApp traffic starts.

### Errors Hit

1. **Hermes installer's setup wizard silently defaulted to "Nous Portal"** when run non-interactively (no one there to answer the prompt). Didn't actually complete OAuth (verified no real credentials were written), but wasted that step — had to configure the API key manually afterward instead.
2. **Playwright Chromium install failed** (`'playwright' is not recognized...`) because the installer's own suggested fix command runs from the wrong directory. Fixed by running `npx playwright install chromium` from `hermes-agent/node_modules/agent-browser/` instead of the repo root.
3. **PATH didn't refresh in already-open terminals** after install (matches the installer's own advice to restart the terminal) — worked around by using the full exe path (`.../hermes-agent/venv/Scripts/hermes.exe`) for the rest of the session.
4. **Real root cause of "it won't respond" bug:** `config.yaml` shipped with `model.provider: auto` *and* a stray `model.base_url: https://openrouter.ai/api/v1` (leftover template default). This combination caused Hermes to auto-detect and try routing through **AWS Bedrock** using the user's unrelated, invalid local AWS/Terraform credentials, instead of the intended direct Anthropic API. Fixed by editing `config.yaml` directly: set `model.provider: anthropic`, deleted the `base_url` line.
5. **`hermes config set provider anthropic` doesn't work** — warned "not a recognized config key" but saved it anyway as a stray unused top-level key. The real key is nested (`model.provider`). Found and deleted the dead top-level key during a later tidy-up pass.
6. **Anthropic billing confusion:** the $100 shown in Claude Code's own settings is a *Claude subscription* usage-credit pool, completely separate from the *Anthropic Console* API credit balance that a raw `ANTHROPIC_API_KEY` actually draws from. First test call failed with "credit balance too low" despite the $100 showing elsewhere. User bought Console credits directly (minimum enforced was $20, not the $5 some docs mention — unconfirmed why, possibly region/processor-specific) and confirmed working.
7. **Stale docs found during a tidy-up audit** (not a bug, but worth knowing the audit caught real issues, not just cosmetics): `agent/.env.example` was never actually read by anything and directly contradicted a correct line in `agent/README.md` about where credentials really live. Removed.
8. **`agent/README.md` documented the wrong command for setting `ANTHROPIC_API_KEY`** — found via a follow-up `/inspect` pass and verified against the real CLI. `hermes config set` only ever writes to `config.yaml` (confirmed via `hermes config set --help` and `hermes config env-path`, which shows `.env` is a completely separate file); there's no CLI setter for secrets. Fixed to say: edit `.env` directly, or use `hermes secrets` for an external manager.
9. **`WHATSAPP_ENABLED=false` in `.env` did not disable WhatsApp.** The gateway still logged "WhatsApp is enabled but not paired" and hard-failed the entire startup (not just WhatsApp) with a non-retryable error. The adapter's own log message hints the fix is to *remove* the key entirely, not set it false — comment the line out fully instead.
10. **Gateway console/stdout is misleading — only prints `WARNING`-level and above.** Successful connections (`INFO`-level: "Connected to Telegram," "✓ telegram connected," "Gateway running with N platform(s)") never appear in captured stdout, only in `%LOCALAPPDATA%\hermes\logs\gateway.log`. A fully healthy, successfully-connected gateway looks identical to a hung one if you're only watching stdout — this caused a working gateway process to get killed by mistake, twice, before switching to tailing `gateway.log` directly.
11. **`HERMES_HOME` on Windows is `%LOCALAPPDATA%\hermes`, not `~/.hermes`** as the official (Linux/Mac-written) docs say. Worth remembering for any future setup on this or another Windows machine.
