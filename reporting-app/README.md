# reporting-app/

Next.js dashboard for a non-technical client to review what the AutoEstate agent has generated — one entry per WhatsApp/Telegram listing, the raw facts sent in, and the generated Instagram/Facebook/Yad2 content split into independently reviewable, editable sections. Not purely read-only: an agent can edit generated content, mark a platform as posted, and set an Instagram posting-mode preference (manual / auto-post immediately / auto-post after edit — the auto options are stored but inert pending a real Meta integration).

**Status (2026-08-04):** the redesigned UI, turn grouping, the Listings and Inquiries pages, four `/inspect` correctness sweeps, role-scoped machine credentials, listing `features`, and per-listing **ref codes with copy-ready WhatsApp ad links** are all merged. Still **only ever run locally** (`npm run dev -- -p 4127` — the flag is mandatory, see below); not deployed to Vercel Pro, which is a tracked next step. (Deliberately not a running PR list — that goes stale on the next merge; `gh pr list --state all` is the source of truth.)

## Data source

Multi-tenant: one Postgres database (Prisma) shared across all customers, each with their own `Customer` row and an isolated set of `Run`/`RunMessage`/`RunPlatformContent`, `Listing`, and `Inquiry`/`InquiryMessage` rows. Each customer's dedicated Hermes instance (see `infra/`) pushes its own conversation turns here over HTTP via the `sync-to-webapp` plugin (`agent/plugins/sync-to-webapp/`) — there's no direct database or filesystem access between a customer's Hermes instance and this app.

- `POST /api/ingest` — the ingestion endpoint Hermes instances call. Authenticated with a per-customer bearer secret (`Authorization: Bearer <secret>`), generated by Terraform at provisioning time and looked up by its SHA-256 hash (`Customer.operatorSecretHash` — the secret itself is never stored). **There are two credentials per customer, scoped by role** (`lib/ingest-auth.ts`): the `operator` secret is valid only on `/api/ingest` and `/api/listings/active`, the `buyer` secret only on `/api/inquiries` and `/api/listings/buyer-view`. The split exists because the buyer instance is public: while both shared one secret, extracting it from that box carried write access to the customer's `Listing` data. One `Run` **row** per Hermes turn (`hermesTurnId`), not per session — a WhatsApp/Telegram session never resets between messages, so a session can span many unrelated listings. **This storage contract is owned by Hermes's sync plugin — don't change its shape without updating the plugin too.** Display-time grouping (`lib/run-grouping.ts`) then merges consecutive turns in the same session into one displayed listing whenever an earlier turn was just the skill's clarifying follow-up question, not a finished listing — see that file's doc comment.
- Everything else in the app requires a logged-in Clerk session, scoped to the signed-in user's own `Customer` row (matched by email on first login, then by `clerkUserId` after that).
- A run's status ("Ready" vs "In progress") is based on whether it has at least one assistant message yet, not on any Hermes-side session state.
- `RunPlatformContent` (edit override, posted flag/timestamp, one row per run per platform) is **app-owned state Hermes never writes** — created lazily on first edit/mark-posted action, not by the ingest route.

## Running locally

Requires `.env.local` with `DATABASE_URL` (Postgres), the two Clerk API keys, **and the four `NEXT_PUBLIC_CLERK_SIGN_IN_URL` / `NEXT_PUBLIC_CLERK_SIGN_UP_URL` / `NEXT_PUBLIC_CLERK_SIGN_IN_FALLBACK_REDIRECT_URL` / `NEXT_PUBLIC_CLERK_SIGN_UP_FALLBACK_REDIRECT_URL` keys** — Clerk's SDK reads those from the environment directly (no code references them), and without them the sign-in buttons route to Clerk's hosted account portal and the committed `/sign-in` + `/sign-up` routes never render. Eight keys total; the same set the Vercel deploy needs.

```bash
npm install   # postinstall runs `prisma generate` (Vercel relies on this too)
npm run dev -- -p 4127
```

**The port is not optional, and `-- -p 4127` is not decoration.** The `dev` script is a bare `next dev`, so without it Next takes **3000** — which is the live Hermes WhatsApp bridge's port. Both Hermes profiles hardcode `AUTOESTATE_INGESTION_URL=http://127.0.0.1:4127/api/ingest`, so an app listening anywhere else is up but unreachable: every sync POST is connection-refused, retries 3× and is **dropped for good** (there is no spool). The bot's replies stay perfect and only the dashboard is quietly missing listings.

This paragraph previously claimed 3000 was "permanently occupied" by the bridge and that Next "auto-falls-back to another port (4127, last time)". Both were wrong and were caught on 2026-07-29 by running it: the bridge was **down** at the time, so 3000 was free and Next bound straight to it — 4127 had only ever been reached by passing the flag by hand. Corollary that still holds: **when the bridge *is* up, never kill port 3000 looking for a free port.** Note the adapter also kills whatever holds its own bridge port on gateway start, so an app squatting on 3000 gets killed from the other direction too.

Check health on an **API** route rather than a page: `curl http://127.0.0.1:4127/api/listings/active` should return **401** (up, auth working). A page-route 500 is usually a transient Turbopack recompile and recovers. Once `allowedDevOrigins` is set in `next.config.ts` (already is, for `127.0.0.1` and `localhost`), either hostname works. Before that fix was in place, the wrong hostname produced a silently blank page with dead buttons (client JS blocked as cross-origin), not an error pointing at the cause.

**Start this app *before* the Hermes gateway.** WhatsApp delivers messages queued during an outage within seconds of the bridge reconnecting (6s, measured 2026-07-29), so a gateway that comes up first can complete a real turn into a dead ingestion endpoint and lose it.

To register a new customer after provisioning their Hermes instance (see `infra/modules/hermes-instance/README.md`), use `scripts/provision-customer.ts`.

## Structure

- `prisma/schema.prisma` — `Customer` (incl. `instagramPostMode`, `operatorTelegramChatId`, `buyerWhatsappNumber`), `Run`, `RunMessage`, `RunPlatformContent`, `Listing` (+ `ListingStatus`, + nullable free-text `features`, + nullable globally-unique `refCode`), and `Inquiry`/`InquiryMessage` (+ `InquiryStatus`) models.
- `lib/listings.ts` + `lib/listing-record.ts` — the `Listing` lifecycle. Skills append a fixed-format "Listing Record" footer to their replies; `listing-record.ts` parses **every** footer in a reply (not just the last), and `/api/ingest` matches on `(customerId, area, rooms, sqm)` to update in place rather than duplicate. Three details of that match are load-bearing rather than incidental: `area` is compared **case-insensitively** (with `%`/`_` escaped — Prisma compiles the filter to `ILIKE`), `rooms`/`sqm` are **rounded to 1 decimal** first, and rows already `SOLD` are **excluded**. The exclusion is why the dedupe guarantee (shipped 2026-07-31) is a *partial expression* index — a plain `@@unique([customerId, area, rooms, sqm])` is case-sensitive and status-blind, and would wrongly block relisting a property that previously sold. One asymmetric fallback (2026-08-04): a `Status: Sold` record with **no** non-SOLD match updates the most recent existing SOLD row for the same identity rather than creating another — so re-announcing a sale is idempotent while a genuine relist-then-sell-again still gets its two rows. A `refCode` is assigned on **create only** and never reissued on update — a code already printed in a live ad must keep resolving to the same property.
- `lib/inquiries.ts` — buyer leads. Two deliberately separate axes: stored `status` (operator triage, NEEDS_OPERATOR→HANDLED) and computed display-only `disposition` (did any bot reply in the thread defer to a human?). **`replyDefersToOperator` is a real coupling with the `buyer-inquiry` skill** — it matches fragments of that skill's canonical defer sentence in both languages, so if the sentence changes, this matcher must too.
- `lib/notify-operator.ts` — best-effort Telegram push to the operator when a lead defers, routed per customer via `Customer.operatorTelegramChatId`. Inert until `OPERATOR_TELEGRAM_BOT_TOKEN` is set.
- `lib/ingest-auth.ts` — shared bearer-secret auth for the machine-facing routes.
- `app/api/inquiries/route.ts` — inbound buyer turns from the locked-down buyer instance. One `Inquiry` per **session** (a buyer thread is one lead to keep together) — the opposite of `Run`'s per-turn key. Best-effort listing linking checks a **ref code first** (exact, wins outright) and falls back to matching an area name in the buyer's message; a buyer arriving by ad link never types an area, so without the code path the best-identified leads were the ones that failed to link.
- `app/api/listings/active/route.ts` — every **non-SOLD** listing with its `status` (widened 2026-07-31 from ACTIVE-only; the path name is kept to avoid a lockstep plugin redeploy), read by the operator instance for digests and locator lookup.
- `app/api/listings/buyer-view/route.ts` — **all** statuses including SOLD, so the buyer bot can be honest about a property being gone. Also the only route exposing `Listing.features` (what lets it answer amenity questions instead of deferring) and `Listing.refCode` (what lets it identify the exact property from the buyer's first message). Neither is exposed on `/active` — the outbound skills have no use for either.
- `app/listings/` and `app/inquiries/` — the Listings and Inquiries pages (the latter with a stat strip, search/status filter, full thread and mark-handled).
- `proxy.ts` — Clerk middleware; the machine-facing API routes above are explicitly listed as public (they use bearer auth, not a Clerk session).
- `lib/db.ts` — customer-scoped Prisma queries and mutations (`getRuns`, `getRun`, `setPlatformEditedContent`, `resetPlatformEditedContent`, `setPlatformPosted`). Both `getRuns`/`getRun` group per-turn `Run` rows into per-listing display groups via `lib/run-grouping.ts` before returning anything.
- `lib/run-grouping.ts` — `groupRunsIntoListings()`, chains consecutive same-session turns into one listing whenever an earlier turn's reply doesn't parse as real generated content (a clarifying follow-up question, not a finished listing), bounded at a 30-minute gap so stray chit-chat or a digest from hours earlier doesn't glue onto the next listing; also derives each closed group's clean display title.
- `lib/customer.ts` — resolves the logged-in Clerk user to their `Customer` row; `updateInstagramPostMode`, `updateOperatorTelegramChatId` and `updateBuyerWhatsappNumber`.
- `lib/ref-code.ts` — per-listing reference codes and the `wa.me` ad deep links that carry them. Generation (a confusable-free alphabet, no `0/O/1/I/L/U`), the `REF-` display prefix, and **strict** extraction: a code is only recognised *with* that prefix, because a bare 5-character run is common in ordinary text and a false match would serve confident facts about the wrong property. Uniqueness is **global**, not per-customer, so a future shared buyer number could resolve a code to a customer before knowing whose data to read.
- `lib/copy-button.tsx` — shared copy-to-clipboard control with honest failure reporting. (`app/runs/[id]/platform-section.tsx` still carries its own equivalent; deliberately not refactored in the same change that introduced this.)
- `lib/platform-content.ts` — splits Hermes's one raw reply into Instagram/Facebook/Yad2 sections (tolerant of heading-style drift; takes the *last* occurrence of each header, not the first, since a rapid follow-up listing can get merged into the same reply — see the **repo-root** CLAUDE.md; this directory's own CLAUDE.md is a one-line import of AGENTS.md); falls back to rendering the raw reply unmodified if a confident split isn't found. Also exports `splitByLanguage` (Hebrew/English split, used for both the mirrored-column display and title derivation) and `deriveListingTitle` (a clean one-line title from a matched listing's Yad2 content, used by `run-grouping.ts`).
- `lib/markdown-components.tsx` — shared `react-markdown` component overrides.
- `app/api/ingest/route.ts` — ingestion endpoint for Hermes instances.
- `app/page.tsx` + `app/run-list.tsx` — list of runs, with client-side search/filter.
- `app/runs/[id]/page.tsx` + `platform-section.tsx` + `actions.ts` — full run detail: per-platform cards (mirrored Hebrew/English columns), edit/copy/mark-posted Server Actions. Renders the merged multi-turn transcript (if any) as a collapsed disclosure at the bottom, parses platform content from the group's last assistant message.
- `app/settings/` — the Instagram posting-mode preference, the per-customer Telegram chat id for buyer-lead alerts, and the buyer-facing WhatsApp number used to build listing ad links.

Every page route **that reads the database** is forced dynamic (`export const dynamic = "force-dynamic"`) — `/`, `/runs/[id]`, `/listings`, `/inquiries`, `/inquiries/[id]` and `/settings` — so they always reflect live data rather than a build-time snapshot. The two Clerk catch-alls (`/sign-in`, `/sign-up`) deliberately do not: they read nothing. Said as "every page route" until 2026-07-30, which was simply false and would have sent someone hunting for a missing export.

All user-facing timestamps render in `Asia/Jerusalem`, pinned explicitly in `lib/format.ts`. Without that they format in the *server's* zone, which is UTC on Vercel — every time 2-3 hours off, and the Today/Yesterday boundary flipping at the wrong moment.
