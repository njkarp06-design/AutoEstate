## ▶ BEFORE YOU SAY "DONE"

Five checks, each earned by a real failure in this repo. Run them before telling me a session is finished — not as a ritual, but because every one of them has caught something that would otherwise have reached a future session as a lie.

1. **Did anything merge this turn?** Re-read the handoff's own claims about PR and branch state. They were written *before* the merge and are now probably wrong. (2026-07-27: the handoff called a merged branch "open, not merged" in two places, including the resume prompt.)
2. **Did a plugin, skill or profile config change?** Merging deploys **nothing** — plugins are physical copies inside each Hermes profile. Run the parity recipe in §5 and redeploy. (2026-07-27: 4 of 5 plugins were still pre-fix hours after the fix was on `main`.)
3. **Corrected a fact, renamed something, or changed how a thing works?** Grep for *every other copy* of it — and that includes **code comments and docstrings**, not just `CLAUDE.md`, `TODO.md` and the handoff. Fixing one of three is how the docs went stale originally. Renumbering a TODO item counts: check the cross-references still resolve. (2026-07-27: the PR that split the machine credential in two left both buyer plugins still saying they reuse the operator's secret — a compiler catches a renamed *function*, nothing catches the sentence telling the next person to reintroduce the bug.)
4. **Cold-read test.** Read only this file's START HERE block plus the handoff, as a session that knows nothing. Do you know the state, the next action, and what not to touch — with nothing stale? If not, fix it now, not next time. **Two ways this check gets faked, both earned 2026-07-30 (I said "ready" three times before it was).** First: grepping for known-bad phrases is not a cold read. That tests whether anything is *wrong*; a cold read tests whether everything needed is *present*, and only the second catches a fact that was never written down. Second: **checks 1 and 3 are structurally blind to a brand-new fact.** Both are diffs — 1 against what changed, 3 against other copies of it — so a fact with no other copies returns a clean pass from check 3 precisely because it hasn't been propagated. That is the same shape as §5's widened parity recipe: *a diff scoped to the keys of a thing that exists cannot report the thing's absence.* So: **any fact discovered late in a turn must be re-run through this check, and specifically through the resume block**, which is the text actually pasted into a fresh session. A fact recorded in the gotchas list but missing from the resume block is a fact the next session does not have.
5. **Is a claim verified or just written?** Anything stated as done should say *how* it was checked. "Verified" without a method is close to useless later, and this repo has twice recorded a cleanup that never happened.

These five all *detect* staleness after the fact. §3 carries the one rule that **prevents** it: never write a commit count, PR range, "as of PR #N" status or file count as standing fact — name the command that computes it instead. Five of this repo's doc defects traced to that single habit.

No automation enforces this — deliberately, see §3. It is a checklist because the alternative was a hook, and that was rejected on mechanism grounds, not quality ones.

## 1. What we're building
I'm building a **productized marketing-automation service**. At its core is a **Hermes agent** — an open-source, CLI-based AI agent — that runs one end-to-end marketing process for a client automatically. Around that core sit two things: **secure configuration** (the client's data and credentials handled properly) and a **small reporting web app** so a non-technical person can see what the agent is doing and trust it.

The end goal: package this cleanly enough to demo and pitch to companies — starting with industries slow to adopt tech — as a finished product that delivers real, visible value.

## 2. Who it's for (so your decisions make sense)
The buyer and end-user is a **non-technical marketing lead** at a small or mid-size company. That drives every decision:
- It must be **simple to observe and trust** — clear outputs, visible results.
- It must be **secure by default** — their data, their credentials, never exposed.
- The value must be **visible** — that's the job of the reporting screens.

Optimise for legibility and trust over cleverness.

2. **Shared vs. dedicated Hermes instance — done.** The Hermes install was previously a shared, general-purpose personal instance (kanban, Notion/GitHub/Google-Workspace skills, custom personalities, etc.), not something presentable to a client. 3. **Supply-chain dependency vulnerabilities (`hermes security audit`: 48-50 known CVEs in installed packages, several HIGH).** Attempted the obvious fix (`hermes update`) — it updated Hermes itself cleanly (with a pre-update backup) but did **not** touch the vulnerable pinned versions, since those are locked by Hermes's own upstream lockfile, not something the updater refreshes. Two decisions/lessons from this build:
- **Two axes on an inquiry, deliberately not merged:** stored `status` (NEEDS_OPERATOR→HANDLED, operator triage, `Mark handled`) vs. computed display-only `disposition` (did the latest bot reply defer to a human?). The disposition heuristic keys on the buyer-inquiry skill's **canonical defer sentence** (HE+EN) — a real coupling: `lib/inquiries.ts`'s `replyDefersToOperator` (shared by the ingest route and the UI) matches stable fragments of that exact sentence, so if the skill's sentence changes, that matcher must too. It is display-only, never a safety boundary.
- **Operator notification (1G): transport = Telegram (user-approved 2026-07-25), per-customer routing built.** The seam (`lib/notify-operator.ts`) fires best-effort on a deferring reply with the buyer's contact attached. Telegram was chosen over email (genuinely free, no provider/domain/deliverability) and over a real WhatsApp ping (which needs an outbound sender the locked-down buyer instance deliberately lacks). Multi-tenant routing is a **shared app-level notifier bot** (`OPERATOR_TELEGRAM_BOT_TOKEN` env) delivering to a **per-customer `Customer.operatorTelegramChatId`** (set on the Settings page; blank = dashboard-only). `OPERATOR_TELEGRAM_CHAT_ID` env remains only as a dev fallback. Still inert until the bot token env + a customer chat id are present — nothing leaves the app without real creds. Creating the notifier bot + setting the token is a deployment step (not done here); per-customer chat ids are self-served in Settings.
- **Dev-server lesson:** the reporting-app's generated Prisma client loads at server *start*, not via hot-reload — after a `prisma migrate`/`generate` that adds models, the running `next dev` on 4127 keeps a stale client and every new-model query 500s until the server is restarted. (Confirmed live here: `/api/inquiries` 500'd until the 4127 server was restarted, then all dry-run assertions passed.)

**1H — the buyer instance (built, live-tested and shipped 2026-07-26 in PR #34).** The `autoestate-buyer` Hermes profile now exists (`hermes profile create autoestate-buyer --no-skills --no-alias`), locked down as designed. Three things worth carrying forward:

**Repo-level skill isolation (decided with the user).** `buyer-inquiry` was **moved** out of the shared `agent/skills/` into a new top-level `agent/skills-buyer/real-estate/buyer-inquiry/`, and the buyer profile's `skills.external_dirs` points there. The alternatives — copying the SKILL.md into the profile's own `skills/` dir, or a Windows junction — were rejected: a copy drifts from the repo source that Terraform/cloud-init ships from, and a junction doesn't survive the move to a Linux image. The directory split is also the thing that makes a future per-customer buyer instance a one-line `instance_role` choice. Net effect verified by resolving each profile's real config, not by reading it: the buyer profile discovers exactly **1** skill, the operator profile exactly **5**, and neither sees the other's — so the operator agent can no longer route to the buyer skill either, which is correct.

**Two real Hermes findings, both non-obvious, both found by running the resolution code rather than trusting the config:**
1. **`platform_toolsets.<platform>` is NOT a complete allowlist.** `_get_platform_tools` ends with a "recover non-configurable platform toolsets" block that runs in *both* code branches, re-adding toolsets that belong to the platform composite but are absent from `CONFIGURABLE_TOOLSETS`. With an explicit `telegram: [skills]` list, `kanban` still resolved as enabled. Only `agent.disabled_toolsets` — applied unconditionally as a final subtraction in `model_tools.py::_compute_tool_definitions` — actually removed it. So layer 2 is load-bearing, not belt-and-braces, and Phase 0(d)'s conclusion needs that caveat attached. (Also note `model_tools.py`'s own docstring is stale on this: it claims `disabled_toolsets` applies only "if enabled_toolsets is None", which the code contradicts.) **Rule: after changing tool config, re-dump the resolved tool list; never assume the allowlist held.**
2. **`skill_manage` cannot be dropped.** The `skills` toolset is all-or-nothing (`skills_list` + `skill_view` + `skill_manage`) and Hermes has no per-tool denylist, so a public instance that needs `skill_view` necessarily also exposes skill *writes* — a prompt-injected buyer rewriting the skill that answers every later buyer is the one genuinely durable compromise available here. Neutered rather than removed: `skills.write_approval: true` **stages** every create/edit/patch/delete for review instead of committing it (it never prompts inline, so it can't hang a gateway), and nobody approves anything on a buyer instance. Also set `curator.enabled: false` (the background curator archives unused skills, and this profile has exactly one — an archive would silently kill the instance), `memory` off at both the toolset and `memory.*` level (durable memory is a cross-buyer poisoning vector), and `vision` off (a public instance processing attacker-supplied images is exactly what makes the deferred Pillow CVEs reachable). Verified end state: the model receives **3 tools** and nothing else.

**A third finding, and the most serious — surfaced only by starting the gateway (2026-07-26).** The tool lockdown does **not** cover gateway **slash commands**, because commands are not tools. On connect the log shows `set_my_commands OK … (53 cmds)`, and `GATEWAY_KNOWN_COMMANDS` holds **68** — including `/profile`, `/model`, `/yolo`, `/update`, `/restart`, `/reset`, `/memory`, `/skills`. Access is resolved by `gateway/slash_access.py`, where `policy_from_extra` computes **`enabled = bool(admin_ids)`** and, when gating is disabled, `can_run()` returns `True` for *every allowed caller* (`is_admin` likewise returns `True` unconditionally). Gating is therefore **off by default**, and since a buyer instance sets `TELEGRAM_ALLOWED_USERS=*`, "every allowed caller" meant **every stranger on Telegram had admin-tier access to all 68 commands** — `/profile` most alarmingly, since switching profiles would hand a stranger the operator's outbound, Listing-mutating skills, defeating the entire role-by-channel isolation the architecture rests on.

Fixed by setting `platforms.telegram.extra.allow_admin_from` (the operator's Telegram id) — which is what switches gating on at all — plus a deliberately minimal `user_allowed_commands`, and the same pair for group scope. Verified by resolving the real policy against both real Telegram ids: the operator is admin (all commands), a stranger gets only `/start` plus the hardcoded `_ALWAYS_ALLOWED_FOR_USERS` floor of `/help` and `/whoami`, and is denied everything else. (`user_allowed_commands` started empty; `/start` was added the same day once a real buyer proved that blocking it breaks every new chat — see the second live test below.) **Generalised lesson: an allowlist of `*` silently promotes every stranger to whatever tier the code grants "allowed" callers. Any Hermes surface whose authorization is derived from the sender allowlist must be re-checked on a public instance — the tool lockdown proves nothing about commands, and neither proves anything about a third surface we haven't looked at yet.** Residual, not fixed: the 53-command *menu* is still registered on the bot, so a buyer sees commands they'll be denied — cosmetic, and suppressing it would need vendored-adapter changes.

**First real end-to-end buyer test, 2026-07-26 — the skill layer passed; the surrounding plumbing had four real defects.** Seven messages sent from the operator's own Telegram account to `@autoestate_buyerdev_bot`. Correct on every count that the skill owns: the price answer came only from the injected block; the SOLD listing was reported honestly and never called available; the Hebrew message got a full Hebrew reply; a missing fact (parking) was deferred rather than invented; the viewing request deferred and asked for contact; the prompt-injection attempt was refused in role without leaking. The canonical defer sentence appeared verbatim in all three deferring replies. The fresh session also called `skill_view` on turn one, loading the skill properly — a useful contrast with the long-lived-session compliance gap in [[project_gateway_footer_omission_bug]]. All seven turns synced as **one** Inquiry (session thread key correct), 14 messages in correct order, `source: telegram`, stored `status: NEEDS_OPERATOR`.

What was wrong was everything *around* the skill — and two of the four were only findable by running a real conversation, not by inspection:

1. **`computeDisposition` keyed on the latest assistant reply only**, so the dashboard showed `auto_answered` for a thread in which the buyer had asked about a sold flat, asked for a missing fact, and asked for a viewing — three deferring turns — simply because the *last* message was the injection refusal, which has no defer sentence. That is precisely the lead an operator most needs to see, displayed as handled. Fixed to `needs_you` if **any** assistant message in the thread defers: once a thread has handed off it needs the human until the operator marks it `HANDLED`, which is what the separate stored `status` axis exists for.
2. **`maybeLinkListing` never fired.** It required the full stored area string (`"Rothschild Boulevard, Tel Aviv"`) to appear in the turn text, but nobody types the city — the buyer wrote "the Rothschild place" and the bot replied "Rothschild Boulevard". Verified against the real rows and real turn text: the old predicate linked **nothing on any turn**; the new one (match the segment before the comma) links turns 1 and 2 and still correctly refuses a turn naming two areas. Known remaining limitation, deliberately not fixed: a Hebrew area mention (`רוטשילד`) still won't match an English-stored area — that needs transliteration, not a looser match.
3. **Hermes injects a first-contact onboarding note** into the very first message ever for a profile, instructing the agent to introduce itself, mention `/help`, and **offer to build a profile of the person** — asking a stranger for their name and occupation, offering a `web_search` to confirm public details about them, and promising to save it with the memory tool (which is disabled here, so the promise was empty anyway). It did exactly that to our first buyer. The gate is "first message ever *for the profile*", not per buyer, so it fires once — but that once is a freshly-provisioned customer's very first real prospect, the worst possible audience. Disabled via `onboarding.profile_build: "off"`. The plain intro still mentions `/help`; suppressing that needs vendored changes, so it stands as a known cosmetic wart.
4. **The running gateway rewrites `config.yaml` and strips every comment**, and will clobber an edit made while it is running (it rewrote the file between a write and a re-read, silently discarding an appended block and leaving a duplicate key). **Edit a profile's `config.yaml` only while its gateway is stopped**, and treat `agent/profiles/autoestate-buyer/config.yaml` in the repo as the documented, commented source of truth — the live file is machine-managed and will lose the reasoning.

Two cases this run could not settle — the ambiguity path (that turn had a clear referent from the previous message, so the model reasonably resolved it instead of asking) and contact capture (no number was ever supplied) — were carried into the second live test below, which closed both.

**Second live test, from a genuine non-operator account (2026-07-26) — closes the two gaps the operator run left open, and found the #1 lead field silently broken.** The flatmate's fresh session passed the two cases that had never been cleanly exercised: a cold `"is it still available?"` with no prior referent produced **one** clarifying question naming the real candidates (the ambiguity path, previously only ever proven by `hermes -z` simulation), and the whole thread stayed isolated from the operator's — two separate `Inquiry` rows on two separate sessions. Hebrew mirroring, missing-fact deferral, and status honesty all held again. Both of the prior session's reporting-app fixes were confirmed working on live data: `disposition` computed `needs_you`, and `maybeLinkListing` linked the thread to **Rothschild Boulevard** (it had linked nothing before the fix).

Three further findings, in order of severity:

1. **`buyerContact` was never captured — the single most important field in the feature, and it was silently null on every lead.** The bot asked for a number, the buyer gave one, the bot even echoed it back ("I've noted your number"), and nothing persisted it. Root-caused from the plugin's own once-per-process log line rather than by guessing: the `pre_llm_call`/`post_llm_call` hooks actually pass `['conversation_history', 'is_first_turn', 'model', 'sender_id', 'task_id', 'telemetry_schema_version']`, while `_resolve_lead` was reading `sender`/`user_id`/`chat_id`/`display_name`/`phone` — **none of which exist**, so both the sender handle and the contact resolved to `None` unconditionally. Two stacked bugs: a wrong kwarg name (`sender_id`, not `sender`), and a wrong *source* — Phase 0(b) had already established that platform metadata never carries a dialable number on either platform, which is precisely why the skill asks for one, yet nothing ever read the buyer's message text where the number actually lives. Fixed by extracting from the message, keyed on **digit count** rather than regex shape alone (strip separators, require 9–15 digits): that accepts `052-4419087` and `+972 52 441 9087` while rejecting exactly the things this domain produces — a price (`3950000`, 7 digits), a date (`2026-07-28`, 8), a room count or floor. Rejecting a real number is recoverable since the transcript is right there; storing a listing price as someone's phone number is not. Verified against every real buyer message in the live `state.db` (one captured, eleven correctly ignored) and then through the **real** `/api/inquiries` route by replaying the actual turn: `null` → `052-4419087`, message count unchanged at 10 (dedup held), listing link retained.

2. **`/start` was blocked for buyers — a regression introduced by the slash-command lockdown.** Capping non-admins at the hardcoded `/help` + `/whoami` floor also caught `/start`, which is not an admin action but the button Telegram shows on every new bot chat. The flatmate's very first tap returned "⛔ /start is admin-only here", i.e. every future buyer's first interaction would have been a permissions refusal. Hermes defines it as *"Acknowledge platform start pings without a reply"* — a no-op that creates nothing and exposes nothing — so it is now in `user_allowed_commands`. Everything dangerous stays denied, re-verified against both real Telegram ids. Worth generalising: **locking a public surface down by allowlist will also catch the platform's own entry points**, and only a real client tapping a real button surfaces that.

3. Confirmed fixed in the same run: the first-contact profile-build/`web_search` note did **not** reappear, and `/model` was correctly refused with the stranger tier.

**The disambiguation defect is fixed — `buyer-inquiry` v0.1.0 → v0.2.0.** The flatmate's ambiguity reply listed *all* listings, including the two `SOLD` ones, under "properties I have on hand right now" with no status shown — so a buyer could pick a property that was already gone and only learn that after choosing. Status honesty held once a listing was chosen (verified repeatedly), which is why this survived every earlier test: it is not a false availability claim but the *menu* presenting sold stock as current inventory. The root cause was a genuine gap in the skill rather than model drift — the "no property identifiable at all" branch said to ask "listing the areas" with no status constraint at all. Fixed with an explicit rule that **anything the skill offers unprompted** (clarifying-question candidates, a list of what's available, a suggested alternative) is `ACTIVE`-only, plus two branches that didn't exist before: exactly one ACTIVE listing means there is nothing to disambiguate, and *nothing* ACTIVE means say so plainly and defer rather than listing sold stock. Verified via `hermes -z` against the real four-listing data: the ambiguous case now offers only the two ACTIVE rows; a buyer who *names* a sold property still gets the honest "it's been sold" answer with alternatives and the verbatim defer sentence (the regression that mattered); and an all-SOLD dataset produces "I don't have any available properties right now" plus a lead capture. The distinction the rule turns on is deliberate — the buyer naming a non-ACTIVE property is answered honestly; the constraint is only on what the skill *puts forward itself*.

One residual accepted rather than fixed: the command-refusal text leaks internal config vocabulary at strangers ("ask an admin to add you to `allow_admin_from`") — vendored gateway text an upstream `hermes update` would overwrite.

Two lessons, and they outlive the script:
- **A cheap model auditing docs will assert a file is missing rather than say it couldn't find it.** A prompt that demands evidence for every claim gets *formatted* evidence, not *true* evidence — the shape of a verification is not a verification. Anything automated that reports repo facts needs its claims spot-checked before they're acted on, and "file X doesn't exist" is the cheapest possible thing to check.
- **A tool that lives only on a stale branch can only ever audit stale files.** That was structural, not bad luck: the sole checkout that gave you the script guaranteed it read 64-commits-old docs. Keeping a diagnostic somewhere its own diagnosis is invalid is worse than not having it.

The commits survive as the tag `archive/doc-consistency-checker` (`git show archive/doc-consistency-checker:.claude/doc-consistency-check.sh`) — free, invisible to `git branch`, and no longer a footgun that needs a "never merge this" caveat in three files. What replaced it is `/docs` and `/fastpassdocs`, which read the code as well as the docs; the script's own differentiator was running unattended, and automation is what this repo rejected.

**How to verify this project's state — the recipes, so they don't have to be rediscovered.** Every one of these caught something real on 2026-07-26; none of them is inferable from the docs alone.

- **What tools a profile's model actually gets** (never trust the config): resolve it. `HERMES_HOME=<profile> python -c` → `_get_platform_tools(load_config(), "telegram")` then `get_tool_definitions(enabled_toolsets=..., disabled_toolsets=...)` and print the names. This is what exposed `kanban` slipping past an explicit allowlist.
- **Which skills a profile can see:** `HERMES_HOME=<profile> python -c "from tools.skills_tool import _find_all_skills; ..."`. Run it for **both** profiles — the isolation claim is about what each one *cannot* see.
- **Who can run which slash command:** `policy_from_extra(cfg["platforms"]["telegram"]["extra"], "dm")` then `.can_run(<real user id>, cmd)` for a real operator id and a real stranger id.
- **Repo↔live parity for plugins:** compare content with CRLF stripped (`git show HEAD:<path> | tr -d '
' | md5sum` vs the live file) — this repo uses `core.autocrlf`, so a raw byte compare gives false mismatches.
- **Repo↔live parity for a profile config:** parse both as YAML and compare key by key, ignoring the machine-written `onboarding.seen` **and every key marked `MACHINE-SPECIFIC` in the buyer config** (`skills.external_dirs`, and `allow_admin_from` / `group_allow_admin_from` under **both** `platforms.telegram.extra` and `platforms.whatsapp.extra`) — those are deliberately real dev values that must change on deploy, so a mismatch there is expected, not drift. The WhatsApp pair joined this list on 2026-07-28; a future platform block adds two more, so read the markers in the file rather than trusting this parenthesis. A textual diff is useless here because the gateway rewrites the file and strips comments.
- **Operator config: does what CUSTOMERS get still match what you TEST against?** This is the one parity pair with no shared file — the dev operator profile's `config.yaml` is *not* version-controlled (unlike the buyer profile, which is tracked precisely because no Terraform buyer module exists yet). Real customers are provisioned from `infra/modules/hermes-instance/cloud-init.yaml.tftpl`; you test against the laptop profile. Nothing keeps them aligned, so they can silently disagree — the same shape as the PR #37 drift, where the module had quietly fallen back to a 2026-07-22 snapshot. To check: render the template in `terraform console` (`templatefile(...)` with dummy vars), strip the heredoc wrapper and CRLFs, parse the embedded `/root/.hermes/config.yaml` out of `write_files`, then compare **only the product-decision keys** against the live dev profile — `plugins.enabled`, `agent.gateway_notify_interval`, and the `display.platforms.*` blocks. Deliberately *not* a full diff: `skills.external_dirs`, `platform_toolsets` and the dev-only blocks (browser/terminal/stt) are legitimately machine-specific and would drown the real signal. **Last run 2026-07-28: 0 drifted keys.**

**Widened 2026-07-28 after it missed something, and the miss is the lesson.** The recipe originally compared `display.platforms.whatsapp.*` specifically, so it compared *settings within a platform the module already had* — and was structurally blind to a platform the module **didn't have at all**. It therefore said "0 drift" while the dev operator profile ran Telegram and the Terraform template shipped none, meaning every customer would have been provisioned WhatsApp-only. **Compare the set of configured platforms first, then the keys within each** — a diff scoped to the keys of a thing that exists cannot report the thing's absence. The same shape applies to `plugins.enabled` (it compares the list, so it is already safe) and would apply to any future per-platform block.
- **What the model was actually sent on a turn:** read `api_content` from the profile's `state.db` `messages` table. Reading the visible reply tells you what happened; `api_content` tells you *why*, including whether a plugin's context block was really injected.
- **What kwargs a plugin hook really receives:** log `sorted(kwargs.keys())` once per process. Assuming the names cost a null `buyerContact` on every lead until this was actually printed.
- **Whether the reporting app is healthy:** check an **API** route (401 = healthy, auth working), not just a page route. A page-route 500 during a Turbopack recompile is transient and recovers; the API staying up proves the agent-facing path is fine.
- **Terraform path arithmetic and file globs:** resolve them in `terraform console`, don't reason about them. `terraform validate` passes on a `fileset()` that matches nothing, so a wrong `path.module/../..` chain looks fine until apply. Running it also revealed that **`fileset()` walks the filesystem, not git** — gitignored `__pycache__/*.pyc` files were being pulled into a content hash and an upload. Anything driven by `fileset`/`file`/`filesha256` needs its output printed, not assumed.
- **Whether a guard inside a Terraform `remote-exec` block actually guards:** assume it does not, until `set -e` is the first `inline` entry. Terraform concatenates `inline` into **one newline-joined script with no shebang and no errexit** (`generateScripts`, `internal/builtin/provisioners/remote-exec`) and reports the script's exit status — i.e. the **last** command's. So a failed check does not stop the commands after it, *and* the provisioner still reports success if its final command succeeds. Established 2026-07-30: `inject_secrets`' sentinel `grep -q` before the destructive `mv` had been believed fixed since 2026-07-22 and was doing nothing — replaying the sequence under plain `sh` overwrote a live `.env` and exited 0. Two ways to check without a server: read Terraform's own `generateScripts`, and replay the `inline` list locally as a joined script. Note `set -e` then makes any legitimately-non-zero command fatal, so audit each one (`cloud-init status --wait` exits non-zero on a *degraded* boot and needs `|| true` plus an explicit assertion).
- **Whether a value in `terraform.tfvars` is actually reaching anything:** resolve it — `terraform console` and print the variable. An **undeclared** root variable in an auto-loaded `terraform.tfvars` is a **warning, not an error**, and `plan`/`apply` succeed with exit 0. Measured 2026-07-30, which is how the example customer stack was found to silently discard `telegram_bot_token`: the module declared it, the wrapper every customer is copied from did not, and the README told you to set it. **A per-customer wrapper must declare every variable its README mentions** — the module declaring it proves nothing.
- **Whether a branch still exists on the remote:** `git remote prune origin` **first**, or ask the remote directly (`gh api repos/<owner>/<repo>/branches --jq '.[].name'`). Remote-tracking refs are never pruned automatically, so a branch deleted on merge keeps appearing in `git branch -a` indefinitely. Measured 2026-07-30, immediately after a merge that had cleaned up perfectly — the stale listing made it look otherwise. Same family as the three traps below: **you measured a stale local view of remote state**, which is this environment's most repeated mistake in every one of its forms.
- **Which gateways are actually running:** filter `Get-CimInstance Win32_Process` by `Name -like 'python*'`, not by matching a profile name against `CommandLine` — your own PowerShell invocation contains whatever string you searched for, so it self-matches and reports a gateway that isn't there. On 2026-07-27 that briefly looked like the *public* buyer bot running unattended, which is exactly the alarm you don't want to raise or miss falsely.
- **Whether a credential someone says they revoked is actually dead:** ask the provider, don't take the report. `GET https://api.telegram.org/bot<token>/getMe` returns 401 for a revoked bot token and the bot's identity for a live one — the token is still sitting in the profile's `.env` either way, so "it's revoked" and "it's revoked but the file looks identical" are indistinguishable by inspection. Confirmed the buyer bot on 2026-07-27. Every credential provider has an equivalent whoami endpoint; a *dead* credential is exactly the claim worth an extra thirty seconds, because a wrong answer means a next session plans around an instance it cannot actually start.

**Scoped buyer credential — the last open security gate, closed 2026-07-27.** The buyer instance held the *same* per-customer secret that authenticates `POST /api/ingest`, so extracting it from the one public box in the product carried write access to the customer's real `Listing` data, up to flipping a property to `SOLD`. Tracked as "the highest-consequence open item in the repo" since the 2026-07-26 sweep. The tool lockdown never addressed it — that constrains what the *agent* can do, not what the *credential* is authorized to reach; the two are orthogonal, which is exactly why it survived a security-focused build.

**Design: two credentials, and the lookup itself is role-scoped.** `Customer.ingestionSecretHash` was renamed `operatorSecretHash` and a nullable, unique `buyerSecretHash` added. `authenticateMachineRequest(request, role)` takes the role as a **required** parameter and queries only that role's column — `operator` for `/api/ingest` + `/api/listings/active`, `buyer` for `/api/inquiries` + `/api/listings/buyer-view`. Deliberately **no fallback that tries the other column**; adding one "for compatibility" would silently restore the shared credential. The required-parameter shape is the load-bearing choice: the alternative — return the role, let each route compare — is a check a future route can forget, and forgetting would look like working code. Here it's a compile error.

**The migration had to be hand-written.** Prisma cannot detect a column rename and generated `DROP` + `ADD`, warning it would discard "1 non-null value" — the live customer's real operator hash. Dropping it would have locked the running operator gateway out of `/api/ingest` until the secret was regenerated and re-injected. A hand-written `ALTER TABLE ... RENAME COLUMN` (plus the index rename) preserved it, so the operator instance kept working with the credential it already held and needed no redeployment. **Generalise: for any Prisma rename, write the migration by hand and read the generated one only as a warning about what you're avoiding.**

Two holes the pre-implementation adversarial pass caught, both real and both now covered by rejection paths in `provision-customer.ts`: a `--role buyer` run against a *nonexistent* customer would have tried to create one, but `operatorSecretHash` is non-null, so it would have half-provisioned a customer whose operator instance could never authenticate (now fails loudly, verified to leave no ghost row); and nothing stopped the *same* secret being registered for both roles, which would look like a correct two-credential setup while rebuilding the single shared credential (now rejected).

Also: Terraform's `ingestion_secret` output became `operator_ingestion_secret` — free, since the module has never been applied. **No buyer secret is generated there:** the buyer box has no Terraform module yet (`instance_role` is deferred), and generating it in the operator module would force a future buyer module to reach into the operator's state. It's minted at provisioning time instead.

**Listing features reach the buyer bot — 2026-07-28.** The buyer receptionist could only answer from seven structured fields, so every amenity question ("is there parking?", "is there a lift?") produced a deferral even when the agent *had* stated it. Not theoretical: in the live dev data "elevator" appeared in 10 stored messages, "parking" and "balcony" in 7 each — all in generated captions, none reachable by the buyer bot, because the `Listing` table had nowhere to put them. A real buyer hit exactly this the same day. Fixed with an optional `Features:` line on the Listing Record footer, a nullable `Listing.features` column, exposure through `/api/listings/buyer-view` only, and injection into the buyer context.

**The design risk was not the feature, it was the new way to be wrong.** Today, absent data reliably produces a deferral. A features list invites the opposite error — *"features say elevator and balcony, so there's no parking"* — an invented **negative**, which is worse than the gap it replaces because a confident "no, there's no parking" reads as authoritative and could lose a real sale. The rule (*a feature not listed is UNKNOWN, never absent*) therefore lives in **both** the skill file and the always-injected plugin text, because only the latter reaches a conversation already in progress. Verified live in both directions: asked about **parking** (not listed) it deferred and asked for a contact; asked about a **lift** (listed) it answered "Yes, the building has an elevator" and nothing more.

**One ordering decision prevented a listing-destroying bug, and the counter-proof is worth keeping.** The footer parser stops scanning at the first unrecognised line. `Features` is the only free-text field, so it is the only one that can wrap — and a wrapped value placed *above* `Status:` breaks the scan before `Status` parses, which (being required) drops the **entire record** from tracking. Empirically: with `Features` last, a wrapped value yields a complete record and loses only the continuation; with `Features` above `Status`, the same wrap yields **zero records**. Hence "Features must be the LAST line", stated in the plugin, all three outbound skills, and the schema comment.

Two further details worth carrying: the value is trimmed **at a comma boundary**, never mid-string, because a raw slice turns `parking` into `park` — inventing a feature, the exact failure the design exists to prevent; and ingest uses `features: record.features ?? existing.features`, so a `just-sold` footer that doesn't restate amenities cannot wipe them (verified: a 7-line sold footer transitioned the row in place and preserved the features).

**A near-miss worth recording as a pattern.** Adding the non-exhaustiveness rule made the injected context header two lines instead of one — which silently broke the plugin's `if len(lines) == 1` check for "every row was malformed", the branch that tells the skill to defer everything. Caught immediately, fixed by keying the check to `len(header)`. **Generalise: a literal that encodes the length of something nearby is a landmine; when you extend that thing, grep for the literal.**

Deliberately **not** extended: `active-listings-context` (the operator-side plugin). Feeding a features list to skills whose job is generating marketing prose invites embellishing it back into copy — the opposite of the buyer-side guarantee. Also expected and not a defect: all four pre-existing listings have `features = null` and stay that way until re-sent. Backfilling from stored captions was rejected outright — extracting facts from marketing prose is precisely the invention risk this design exists to prevent.

**Channel consolidation — decided 2026-07-28. One number per customer, not two.** The question raised: must every new customer really cost two new phone numbers (the operator-facing bot they message, and the public buyer-facing bot), and does migrating to the WhatsApp Cloud API remove that? **Cloud API does not.** The number count is driven by **roles × customers**, and the two *roles* are forced by Hermes's own gating, not by WhatsApp. What Cloud API changes is the cost of each number, not how many there are — so it had to be paired with something that attacks the *role* factor.

**Decided: move the operator channel to Telegram, the buyer channel to the official Cloud API.** *Operator → Telegram:* bots need **no phone number at all**, are free and unlimited, and the path is already built and live-tested (it was the pre-eSIM stand-in, and is now a real buyer channel). The asymmetry that makes this safe to ask for: the operator is a **paying customer being onboarded**, so "install Telegram and tap this bot" is a reasonable request; a buyer who just tapped a Yad2 ad is not someone you can ask that of, which is exactly why the buyer side must stay on WhatsApp. The cost is real and accepted — it cuts against the brief's "WhatsApp-native, no habit change" premise for the agent, though not for the buyer, where it actually matters. *Buyer → Cloud API:* one Meta app / WABA hosts **many numbers**, each with its own `phone_number_id`, all delivering to **one webhook** — no eSIM, no handset, no OTP, no 14-day keepalive, no ban risk, and the customer can advertise their real business number. Net: **one number per customer**, minted from Meta rather than a SIM shop. Both are gated on Hetzner (Cloud API needs a public HTTPS webhook, which the module's no-inbound-but-SSH firewall forbids); the operator→Telegram half is not, and is config rather than code.

**Rejected as the destination, adopted for two narrower uses: one shared buyer number for all customers.** The mechanism is real — every listing gets a short `refCode`, the ad's contact link becomes a WhatsApp deep link with prefilled text (`wa.me/<number>?text=…REF-4821`), so message one identifies both the customer *and* the exact property. Binding must then be sticky and server-side: one endpoint (`POST /api/buyer-context` with `{sessionId, senderPhone, latestMessage}`) looks up an existing binding, else extracts a code and binds, else returns `unbound` — the plugin stays dumb, fetching and injecting exactly as `buyer-listings-context` already does. Binding on the buyer's **phone**, not only the session, makes a returning buyer resolve with no code. **Three objections, the first decisive:** buyers routinely clear prefilled text and just type "hi", and an unbound buyer has no listings, no agent identity and no operator to notify — an **unattributed lead is a lost lead**, precisely what the feature exists to prevent; the conversation happens on AutoEstate's brand rather than the agent's own advertised number, so they don't own their lead history; and one number carrying every customer's stranger traffic is a single point of failure that on **Baileys is disqualifying** (that volume profile is the ban profile, and one ban takes down every customer at once) — so this only makes sense layered on Cloud API. **Where it does earn its place:** as an **onboarding bridge**, since per-customer Meta business verification is the slow part of the plan and a shared number lets a new customer go live the day they sign, migrating to their own Cloud number once verification clears; and as a **cheap/trial tier**, where the missing own-brand becomes the upsell.

**Worth taking from that design regardless of whether the shared number is ever built: per-listing ref codes.** A code in the deep link means the bot knows the exact listing from message one, so `buyer-inquiry`'s whole disambiguation branch — the one rewritten in v0.2.0 after it offered SOLD listings as if on the menu — mostly stops firing. That is a UX win with none of the shared-number downsides, and it is a prerequisite for the shared number anyway, so it is the sensible first build step whichever way this goes. **Not started; no schema change made.** Nothing account-level was actioned — no numbers bought, no Meta verification begun.

It is: `pre_llm_call` receives `sender_id=getattr(agent, "_user_id", None) or ""` (`agent/turn_context.py:740`, verified by reading the vendored source, and `sync-inquiries-to-webapp` has consumed it since 2026-07-26). The claim dates from the 2026-07-25 buyer-inquiry planning pass and was superseded the next day by the null-`buyerContact` fix, which is what found the real kwarg list. **The architectural conclusion is unchanged and the four other sites saying sender identity "never reaches a *skill*" remain correct** — a plugin knowing the sender only lets it *inject text*, and this repo has documented three separate times ([[project_gateway_footer_omission_bug]], PR #26, PR #28) that in-context text does not reliably make the model withhold an action. Role-by-channel isolation is still forced. Recording it because it is exactly the kind of superseded-but-confident sentence §3 warns about, and because a future session evaluating a shared-instance design would otherwise conclude the sender is unknowable when it is not.

**Per-listing ref codes built (TODO 12d) — 2026-07-28.** The first half of the channel-consolidation work, and the half that pays off regardless of what happens to transports. `Listing.refCode` (a short code like `K7M2P`, shown as `REF-K7M2P`) is assigned at ingest and carried into the ad's WhatsApp deep link (`wa.me/<number>?text=Hi, I'm interested in REF-K7M2P`), so a buyer's first message identifies the exact property and `buyer-inquiry` stops having to guess. Also added `Customer.buyerWhatsappNumber`, purely to build those links — it is a display value, never configuration the gateway reads.

**Four design decisions, each of which changes behaviour if reversed.** *Uniqueness is global, not per-customer*, because a future shared buyer number (12c) must resolve a code to a customer **before** it knows whose data to read — free now, impossible to retrofit once codes are printed in real ads. *A code is assigned on create and never reissued on update* — an ad already running must keep resolving to the same property, so the ingest update branch deliberately leaves it alone. *Matching requires the `REF-` prefix*: a bare 5-character alphanumeric run is common in ordinary text, and a false code match serves confident facts about the wrong home, whereas a missed one degrades to the existing area matching — the failure directions are asymmetric, so the regex is deliberately strict rather than helpful. *The alphabet excludes `0/O/1/I/L/U`*, because codes get read off phone screens.

**The measurement that justified the retry loop.** 20,000 generated codes produced **19,992 distinct** — 8 collisions, right at the birthday-paradox expectation for a 24.3M space. `allocateRefCode`'s retry is therefore load-bearing at real volume, not defensive decoration, and it returns `null` rather than throwing on exhaustion: failing would abort the transaction and lose the `Listing` row entirely, which is strictly worse than a listing you can't deep-link to — the same silently-untracked-listing failure this file has produced twice before.

**A structural limitation, stated because it looks like an oversight.** The agent never learns a listing's code from the WhatsApp reply — the code is assigned at *ingest*, after that reply has already been sent. They get it from the dashboard. Putting it in the reply would mean generating codes agent-side, which forfeits global uniqueness; the ordering is a real constraint, not a missing feature.

**Verification.** Extraction unit-tested 18/18 including every false-positive case that matters in this domain (a price, a phone number, a street number, `REFUND`, wrong length, out-of-alphabet characters, Hebrew context). Ingest exercised through the **real** route with a throwaway customer: create assigns a code, an update transitions the same row with the code unchanged, a sold footer preserves both code and features, a distinct property gets a distinct code, and global uniqueness held across the table — with cleanup **proven by querying for residue**. The plugin's four degrade paths were *executed*, not read: all-malformed and empty both return the explicit no-listings context, a legacy `refCode: null` row still renders (no `REF-None` leak), and a dead endpoint returns `None`. `next build` was run for real (dev server stopped first) specifically because this change adds a `"use server"` export, the one error class `tsc` and `eslint` both pass. Not live-tested with a real buyer — no ad link has been tapped by an actual person.

**Live-tested the same day, and it immediately found a defect the feature itself had introduced.** A real tapped ad link resolved `REF-V42TS` straight to Rothschild with no disambiguation question, deferred honestly on an unlisted feature (parking) and answered a listed one (elevator) — and `api_content` for that turn confirmed the injected `REF CODES` rule and code-bearing row genuinely reached the model, which no dry run had ever proven. But the lead **failed to link to its listing**: `maybeLinkListing` matches an area name *in the buyer's message*, and a buyer arriving by ad link never types one — their entire message is "Hi, I'm interested in REF-V42TS". So ref codes made the **best-identified lead in the system** link *worse* than the vaguer "the Rothschild place" phrasing that preceded them. Fixed by checking codes first (exact, wins outright; a code matching nothing falls through to the area match rather than returning), proven by replaying the real turn through the real route.

**Transliteration is why a code beats an area, and a live test proved it by accident (2026-07-28).** A real operator message typed `sheinkin`; the model recorded the area as `Shenkin`. Not a fault — it normalised a real street name — but `maybeLinkListing` does substring matching, so a buyer typing the *other* spelling would match nothing. Hebrew street names have no single Latin spelling (Sheinkin/Shenkin/Shinkin, Rothschild/Rotschild), and both ends of that comparison are free text produced by different people at different times. Area matching is therefore inherently brittle **in this market specifically**, and no amount of loosening fixes it without inviting false positives. A ref code sidesteps the whole class: it is an exact token the buyer carried from the ad. That is an unplanned validation of making the code win outright over prose inference, rather than treating it as one more signal.

**The lesson is about the shape of the testing, not the bug.** Every dry run had exercised ingest → `Listing`; not one touched the *inquiry* linker, because that path has no footer and no structured marker, so it never came up. A feature that changes **what buyers type** silently invalidates every heuristic keyed on what buyers used to type — and those heuristics can live in a different file, on a different route, behind a different credential. **When a change alters the shape of real user input, grep for every consumer of that input, not just the one you're editing.**

**Note the plugin header grew from two entries to three.** The `len(lines) == len(header)` guard that detects "every row was malformed" was already keyed to `len(header)` rather than a literal, so it survived — which is the 2026-07-28 landmine lesson paying for itself one revision later.

**Outbound file delivery — a fourth isolation layer nobody had looked at, closed 2026-07-29.** A feature question (can the agent send listing photos/videos, and can the buyer bot forward them?) turned into a security fix, because scoping it meant reading how Hermes delivers files at all.

**The mechanism is the finding: outbound media is not a tool.** The model emits a path in its reply **text**; the gateway strips it and dispatches the file (`gateway/run.py` → `send_video`/`send_multiple_images`/`send_document`). **And there are two triggers, not one — corrected 2026-07-31, when every copy of this claim in the repo said `MEDIA:` alone.** `extract_media` handles an explicit `MEDIA:<abs path>` tag; `extract_local_files` handles a **bare** absolute, `~/` or Windows drive-letter path *merely mentioned* in the reply, if it carries a recognised extension and passes `os.path.isfile()` — its own docstring gives the intent, shipping artifacts "without needing an explicit `MEDIA:` tag". Both run on every reply, chained in `gateway/run.py`. **The PR #67 lockdown covers both**, so this was a documentation gap rather than a second hole: `filter_media_delivery_paths` and `filter_local_delivery_paths` each call the same `validate_media_delivery_path`. Verified by reading both call sites and both filters, not inferred from the tag's name — which is exactly how the narrower claim survived a security-focused read. Every isolation layer this project built constrains something else — the skill layer controls which skills load, the tool layer controls which tools the model receives, the credential layer controls what the secret can reach. **None of them touches a mechanism triggered by ordinary reply text.** The buyer instance's celebrated 3-tool lockdown is simply not in the path, and `agent.disabled_toolsets` has nothing to say about it.

Hermes defaults to `gateway.strict: false`, which delivers any existing file not on a credential denylist — and that denylist is scoped to the **active profile** plus the shared root, so it does not cover a sibling profile. Measured by running `validate_media_delivery_path` with `HERMES_HOME` set to the buyer profile, per the standing rule that a security claim must be executed rather than read: the buyer's own `.env` and `auth.json` were already blocked, but **`autoestate/.env` (the operator's Anthropic key, bot token and ingestion secret), `autoestate/state.db`, and the buyer's own `state.db` (every buyer's messages and captured phone numbers) were all deliverable.** Hermes's own docstring says strict mode is "suitable for public-facing bots where prompt injection from one user shouldn't be able to exfiltrate the host's secrets to that same user" — which is a precise description of this instance, shipped off by default.

**Fixed with two keys, and the second is the one worth remembering.** `gateway.strict: true` alone does **not** close it: strict mode keeps a recency fallback that delivers anything modified within 600s, on by default. Its rationale is explicit — injection targets "have mtimes measured in days or months" — and that is true of `/etc/passwd` and **false of the file that matters most here**, because the profile's `state.db` is rewritten on every turn and is therefore permanently inside the window while the gateway runs. Tested rather than assumed: with strict alone, a freshly-touched `state.db` came back **delivered**; with `trust_recent_files: false` as well, blocked. Legitimate delivery is untouched — the cache roots are honoured *before* the denylist, so `cache/{images,audio,videos,documents}` stay deliverable, which is exactly where a future media feature must write. Verified in the worst case (every target `utime`d to now): 5/5 blocked, cache probe still delivered, probe cleanup proven by query, repo↔live parity 0 drift. The buyer gateway was stopped throughout, so it takes effect on its next start and no restart was performed. **Deliberately not changed on the operator instance** — single-tenant, only the customer messages it, so the threat model differs; settle it at first `terraform apply` alongside the slash-command gating question rather than blind.

**Two lessons, and the first generalises past this repo.** *An isolation layer only constrains the mechanism it was built for.* This project reasoned carefully about skills, then tools, then credentials, and each time concluded the public instance was safe — but every one of those layers gates a **capability the model invokes**, and `MEDIA:` is a capability the model *writes*. When assessing what a locked-down agent can do, enumerate what its **plain output text** can trigger downstream, not just what its tool list allows. Nothing about the tool lockdown was wrong; it was answering a different question than the one that mattered. *And second:* the fix that passed on the first try was incomplete, and only survived because the neighbouring case got tested. Strict mode blocked all five targets — a clean PASS — and would have shipped as done if the recency fallback hadn't been read afterwards and the "but `state.db` is written every turn" case tried explicitly. That is the same shape as the `_extract_phone` half-fix (2026-07-27): **when a guard's own documentation explains which case it defends against, test the cases it doesn't name.**

**Blob store for listing media — Cloudflare R2, decided 2026-07-29.** The one decision that unblocks TODO item 13's design, taken before any of it is built. Nothing account-level was actioned: no Cloudflare account, no bucket, no credentials.

**The deciding factor is egress, and it is a property of this architecture rather than of the file sizes.** Media is produced on the operator instance and consumed on the *buyer* instance — a different machine in production — so every file crosses the network at least twice before a buyer sees it, plus dashboard views, plus a re-fetch per buyer request unless the buyer box caches. Storage is bounded by listing inventory; **egress scales with usage**, which is the axis that grows with success. R2 charges zero egress, which switches that axis off entirely. Second reason: R2 is S3-compatible, so `@aws-sdk/client-s3` in the Next.js app and `boto3` on the Hermes box are the same API, one credential model, two runtimes.

**Rejected, with the reasoning that would otherwise be re-derived.** *Vercel Blob* would be the right call if media were only ever displayed in the dashboard — `put()` is a one-liner inside the platform the app already deploys to — but the buyer box is a first-class consumer sitting on Hetzner, outside Vercel, which turns its main advantage into irrelevance while still paying transfer; it also has **no Python SDK**, so the Hermes half would be hand-rolled HTTP against a proprietary API. *S3* re-imports precisely what AWS was already rejected for on compute: per-GB egress plus IAM overhead. *Backblaze B2* is genuinely competitive and would be no mistake; R2 won on zero-egress being unconditional rather than a storage-ratio allowance.

**Two design consequences settled at the same time**, both cheap now and awkward later. **Private bucket, per-customer key prefix, presigned URLs — never public objects**, because a public URL is a permanent unauthenticated link to a customer's property media and there is no revoking it once it is in a WhatsApp thread. And **the buyer box gets a read-only, prefix-scoped credential, never the operator's** — the same split, for the same reason, as the operator/buyer ingestion secret closed on 2026-07-27: it is the one public box, and a tool lockdown constrains what the *agent* can do while saying nothing about what its *credential* can reach. That distinction has now caused two separate findings here, so it is worth stating as a standing design rule rather than rediscovering it a third time.

**A framing correction worth keeping, because it was the owner's catch.** This was first put to them as "a new dependency and a real recurring cost". The cost part is wrong at the scale in question — the free tier covers a pilot several times over, so the expected bill is zero. The reasons it still required sign-off are §6's actual words: it is a **new external service dependency** and creating the account is an **account-level action**, both of which hold at zero cost. *Generalise: when invoking a guardrail, cite the clause that actually applies. Reaching for "it costs money" when the real objection is "it is a dependency I should not choose silently" makes the guardrail look like it is about budget, and a reader who checks the price will reasonably conclude the guardrail does not apply.* Also verify R2's current pricing at signup rather than inheriting the projection above — this repo has already been bitten once by stale third-party pricing (see the Meta per-message change in the channel-consolidation entry).

**The WhatsApp outage is over, and the recovery taught more than the outage did — 2026-07-29 (evening).** A live-operations session, no repo artefact deployed. **The recovery finding, and it is the one worth carrying: the operator never needed re-pairing.** Its device link had never been logged out — the incident merely moved the session files aside, so the gateway saw no `creds.json` and said "enabled but not paired", which reads identically to a dead link. Check the phone's Linked Devices list and try the preserved session first; it costs a file copy.*

**A near-miss that would have been serious, and it came from a tool doing something reasonable.** `hermes whatsapp` re-runs **first-time setup** whenever it cannot see existing `WHATSAPP_*` values — precisely the state the outage mitigation had left the operator profile in — and asks "Who should be allowed to message the bot?", writing the answer straight into `.env`. The answer given was `*`, which is *correct on the buyer profile* and put `WHATSAPP_ALLOWED_USERS=*` onto the **operator** one: all five outbound `Listing`-mutating skills, no tool lockdown, and slash gating off (it is enabled only by an admin list's presence, so every allowed caller holds admin tier on ~68 commands including `/profile`). It was never live — the running gateway had WhatsApp disconnected and was not restarted — and was restored from the pre-incident backup. *Two things generalise. **A destructive default can hide behind an identical prompt**: the same wizard question means opposite things on two profiles and it cannot tell them apart. And **a mitigation that works by removing configuration will be undone by the next tool that re-adds it** — the commented-out `.env` is what made the wizard think this was a fresh install.*

**Three more findings, each measured rather than reasoned:**

1. **Neither commenting out `WHATSAPP_*` nor `WHATSAPP_ENABLED=false` disables WhatsApp.** Resolved through `load_gateway_config()` per profile, with the value supplied in the real process environment and re-printed after the load so dotenv precedence was visible: on **both** profiles WhatsApp resolves `enabled: True` with the var absent, `=false`, and `=true`.
